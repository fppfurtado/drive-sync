# Backlog

## Próximos

- config: permitir override de `git_mode` por subpath dentro de um folder — hoje `git_mode` é por folder inteiro (ex.: dev-projects=bisync se aplica a todo `/storage/3. Resources/Projects/`). Repos com `.git/` cronicamente problemático (caso real em 2026-05-13 a 14: `tjpa/pje-2.1` acumulou 3 tentativas de bisync `--resync` falhando ~19h totais com `Code=2003`/`Code=2500`/`Code=2501`/`gopenpgp` no rclone+protondrive, enquanto outros subrepos do mesmo folder e a library [git_mode=off] funcionaram de primeira) deveriam poder cair em `git_mode: bundle` ([git_handler.py](drive_sync/git_handler.py), CLAUDE.md → "git_mode Semantics") sem o operador ter que extrair o subdir em folder top-level separado. Direção preferida (validar antes de virar plano): `subpath_overrides:` na entry de folder no config.yaml, com `subpath: <rel>` + `git_mode: bundle` (mais campos quando justificado). Alternativa descartada: auto-fallback após N falhas — mais inteligente mas exige threshold + storage de estado por subárvore; config explícito > inferência alinha com a doutrina do projeto. Workaround hoje sem código novo: folder entry top-level para o subpath problemático com `git_mode: bundle`; dedup via `owning_folder()` no [watcher.py](drive_sync/watcher.py) cuida do roteamento — funciona, mas polui o config e perde visibilidade de que a entry é override do parent. **Pré-requisito antes de pôr em prática:** item abaixo (rate-limit por folder) — sem ele, bundle re-uploadar a cada evento do watchdog é proibitivo para repos com `.git/` na casa dos GB.

- repo: criar `.worktreeinclude` listando `config/config.yaml` e `.claude/settings.json` para replicação automática em worktrees criadas pelo /run-plan — sem o arquivo, gitignored em uso não são propagados e validações que dependem deles (config local, settings do Claude) ficam mancas. Capturado em pré-loop do /run-plan auth-pause-on-failure (2026-05-12).

- sync_engine: avaliar cobertura do classificador para `Code=10013, Status=400` em `/api/auth/v4/refresh` (`Invalid refresh token`) — observado em produção pelo code-reviewer durante /run-plan auth-pause-on-failure, fora do escopo do classificador atual (que cobre só 8002/9001 + Status=422 em `/api/auth/v4`). É o sintoma do race do [ADR-001](docs/decisions/ADR-001-serializar-chamadas-rclone.md) quando escapa; não é benigno mas também não exige TOTP humana. Decidir se vira terceiro `kind` no `AuthDegradedError` (`refresh_token_invalid`?) ou se fica de fora porque tende a se auto-resolver na próxima tentativa.

- ADR-001: avaliar se a limitação "múltiplas instâncias concorrentes do daemon" precisa ser documentada explicitamente — flagged pelo code-reviewer durante /run-plan de [serialize-rclone-calls](docs/plans/serialize-rclone-calls.md) como cenário potencialmente não coberto pela seção "Limitações" atual (que só fala de rclones invocados fora do daemon, ex.: operador no terminal). Cenário improvável na prática (systemd `Type=simple` não permite duas instâncias normalmente; só durante upgrade ou crash recovery) mas merece avaliação para fechar o escopo.

- install: investigar regressão do symlink `~/.local/bin/drive-sync` — em 09/mai 2026, ao restartar o daemon depois do fix do estado de listings de library/archive, descobri que o symlink que deveria apontar pro venv pipx (`/home/fppfurtado/.local/share/pipx/venvs/drive-sync/bin/drive-sync`) estava sobrescrito por arquivo regular com shebang `#!/usr/bin/python3` (mtime 07/mai 15:06), causando `ModuleNotFoundError: No module named 'drive_sync'` em loop sob `Restart=` do systemd. `pipx list` reportava `drive-sync (symlink missing or pointing to unexpected location)`. Fix imediato: recriar o symlink manualmente. `scripts/install.sh:22` usa `pipx install --force` corretamente — não é a causa direta. Suspeita primária: `pip install -e .` documentado em [.claude/CLAUDE.md:22](.claude/CLAUDE.md) como alternativa de dev sobrescreve o entry-point do pipx em `~/.local/bin/` quando rodado contra o Python do sistema (Fedora `pip --user` instala scripts no mesmo prefixo). Investigar: (1) reproduzir o cenário (`pip install -e .` no Python de sistema e verificar se quebra o symlink); (2) ajustar CLAUDE.md para recomendar venv isolado de dev (`python -m venv .venv && .venv/bin/pip install -e .`) e/ou avisar do conflito; (3) considerar adicionar `pipx reinstall drive-sync` como recovery hint no install.sh. Conexão com o item anterior do backlog (health-check de auth): o mesmo tipo de gap de observabilidade — daemon em loop de restart por 18 horas até intervenção manual; defesa em profundidade unificada (sd_notify + pause-on-failure) cobriria ambos os modos de falha (auth e startup).

- install: trocar `pipx install --force` por `pipx install -e .` (editable) + criar `scripts/update.sh` (`git pull && systemctl --user restart drive-sync`) — hoje toda feature nova exige reinstall manual via pipx para a CLI ver o código atualizado (descoberto em 10/mai 2026 quando `drive-sync --status` recém-mergeado falhou com `unrecognized arguments`). Editable mata o passo de reinstall: pipx aponta o entry-point pro checkout, `git pull` basta para CLI one-shot. Daemon ainda precisa de restart pra reimportar módulo (Python não faz hot-reload), então o `scripts/update.sh` encapsula o ritual completo. Trade-off: editable amarra o caminho do checkout — mover/renomear o projeto quebra o entry-point; no setup atual (single-user, projeto syncado pelo próprio drive-sync para o mesmo path em todas as máquinas) é favorável. Conexão com o item `install: investigar regressão do symlink` acima: aquele suspeita que `pip install -e .` contra Python de sistema sobrescreve o entry-point pipx; mover o dev workflow para um único pipx editable elimina o conflito (não há mais dois lugares competindo pelo mesmo `~/.local/bin/drive-sync`) — provavelmente os dois itens viram um plano só em /triage. Em produção real multi-máquina o padrão profissional seria release tag + wheel publicada, mas é overkill aqui.

- daemon: mitigar latência de pasta pequena bloqueada por sync grande no front rclone — após serialização ([ADR-001](docs/decisions/ADR-001-serializar-chamadas-rclone.md)), a premissa "arquivo grande não bloqueia outros" do [CLAUDE.md](.claude/CLAUDE.md) cai: pasta pequena espera atrás de pasta grande na fila rclone. Preempção real (SIGSTOP/kill+resume do bisync em curso) **descartada como inviável** — rclone bisync não é preemptível: segura conexões HTTP com Proton + estado interno, e matar produz `Bisync aborted. Must run --resync to recover` (perda total de progresso, observado no /debug de 07/mai 2026). Construir camada de checkpoint/retomada por cima do rclone seria reescrita do sync_engine, não item de backlog. Direções viáveis a avaliar em /triage antes de virar plano: (1) **granularidade** — subdividir pastas grandes em jobs menores no config (ex.: cada subdir top-level de Projects vira um job); pasta grande continua serial internamente, mas libera o lock entre jobs e cede turno a outras. Watcher já suporta sub-path dedup via `owning_folder()`. (2) **fila com prioridade** — pasta pequena/recém-modificada fura a fila quando worker libera; não preempta o que já roda, só ordena pendentes. Gatilho de revisão: se rclone#7381 for resolvido upstream e a ADR-001 for substituída (paralelismo restaurado), este item fica obsoleto.

## Concluídos

- daemon: sinalizar pasta degradada após >12h sem sincronização bem-sucedida — estender ADR-003 (hoje cobre só auth Code=8002/9001) com gatilho temporal per-folder, sem pausa global. Cobre falhas bisync genéricas (ex.: `march failed: directory not found` em flakiness do protondrive) que hoje passam silenciosas até inspeção manual de journalctl. Sinalização tripla: `STATUS=degraded folders: <list>` (sd_notify), `notify-send`, log `[FOLDER_DEGRADED]`. Reset por sucesso da pasta. Incidente: dev-projects 7 dias parado em maio 2026.

- watcher/daemon: `min_interval_between_syncs` (ou `cooldown_seconds`) por folder — rate-limit por pasta independente do `debounce_seconds` (que só agrupa eventos da mesma rajada) e do `periodic_full_sync_seconds` (que é safety-net global). Hoje, qualquer toque em qualquer arquivo da pasta dispara job assim que o debounce vence. Para folders com custo de sync alto (caso típico: `git_mode: bundle` em repo com `.git/objects/pack/` de GBs — cada job re-uploadar o bundle inteiro porque rclone não faz delta upload de blob), o ideal é colapsar atividade num intervalo longo parametrizável (ex.: 4h). Semântica: ao receber evento na pasta, se `now - last_sync_at < cooldown`, agendar para `last_sync_at + cooldown` em vez de disparar; eventos subsequentes dentro da janela são absorvidos. Implementação provável: estado in-memory no daemon (`_last_sync_at: dict[str, float]`), comparado antes de enfileirar. Sem persistência cross-restart inicialmente (cooldown reseta no restart — ok, gera no máximo um upload extra). Direção a validar antes de plano. Bloqueador de fato para o caso real do tjpa/pje-2.1 sob bundle mode.

- notifier: substituir subprocess `systemd-notify` por escrita direta em `NOTIFY_SOCKET` — sob `NotifyAccess=main` o PID do child do subprocess é rejeitado, travando `systemctl start` em timeout (READY=1 perdido) e silenciando `STATUS=degraded:` quando auth-pause dispara. Diagnóstico em /debug 2026-05-12 (toggle empírico `NotifyAccess=all` confirmou); fix em [docs/plans/notifier-direct-socket.md](docs/plans/notifier-direct-socket.md) — socket Unix DGRAM stdlib, sender = MainPID, sem nova dependência PyPI. ADR-003 preservada.

- daemon: health-check de auth + pause-on-failure — detectar `Code=8002`/422 em qualquer job, marcar daemon como degraded (`sd_notify` ou similar), pausar workers e disparar `notify-send`. Hoje, falha de auth produz 26 erros/10min antes de qualquer sinalização (descobri por acaso 5 dias depois). Defesa em profundidade que vale mesmo com a serialização aplicada — qualquer erro de auth futuro (regressão upstream, mudança da Proton, etc.) fica visível em segundos em vez de horas/dias. Tradeoff: `notify-send` exige sessão gráfica ativa; em headless precisaria canal alternativo (registrar como follow-up se virar caso real).

- CLI `drive-sync --status` para visibilidade observacional do daemon — snapshot one-shot lendo markers do bisync (`~/.cache/rclone/bisync/`) e `config.yaml` para mostrar pastas configuradas, última sincronização por pasta e estado de inicialização. TUI live, controle (forçar sync/pausar pasta) e expor estado in-memory via IPC ficam como follow-ups separados.

- unit systemd: relaxar hardening removendo `ProtectSystem=strict` para destravar bisync sob protondrive — diagnóstico do /debug 07/mai 2026 (após 9+ dias de loop EROFS no `dev-projects` bloqueando 15549+ arquivos de `h3/gestaoclick-report_react/.git/objects`) isolou a unit systemd como variável discriminante: rclone bisync com flags idênticas executou 2h58min manualmente sem EROFS, e falhou em ~33min sob a unit. Trade-off (defesa em profundidade reduzida vs. funcionalidade) registrado em ADR-002.

- bisync: investigação do EROFS espúrio em pastas grandes (`chtimes`/`mkdir`/`.partial: read-only file system`) — diagnóstico fechado em /debug 07/mai 2026: causa = unit systemd interferindo com rclone+protondrive backend. Experimento controlado isolou a unit como variável discriminante (rclone bisync com flags idênticas executou 2h58min manualmente sem EROFS; ~33min até falhar sob a unit). Hipóteses falsificadas no caminho: corrupção do FS (btrfs sadio), race entre instâncias rclone do daemon (lock ADR-001 já em produção), concorrência interna do rclone (`--transfers=1 --checkers=1` reproduziu igual). Trade-off (relaxar hardening vs. funcionalidade) e plano de fix em [ADR-002](docs/decisions/ADR-002-relaxar-hardening-systemd-protondrive.md) e [docs/plans/relax-systemd-hardening.md](docs/plans/relax-systemd-hardening.md).

- sync_engine: serializar chamadas rclone (asyncio.Lock module-level envolvendo `_run`) para corrigir race condition no token refresh do backend protondrive — disparada quando ≥2 instâncias rclone fazem init do backend simultaneamente (cenário recorrente na nossa config: `periodic_full_sync` enfileira 12 pastas/h e `max_concurrent_jobs=3`). A cada ~5 dias zera `client_uid` e `client_salted_key_pass` no `rclone.conf`, exigindo reauth manual via TOTP. Causa-raiz isolada por /debug em 07/mai 2026 com concordância qualitativa de [rclone#7381](https://github.com/rclone/rclone/issues/7381) (mantenedor henrybear327). Fix é ~5 linhas + teste verificando que chamadas concorrentes serializam. Trade-off aceito: paralelismo dos workers vira ilusão (todo trabalho útil é rclone), mas o lock fica na fronteira correta — subprocess rclone, não a lógica de fila/dedup do daemon.
